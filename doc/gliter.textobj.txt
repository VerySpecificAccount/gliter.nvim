1. gliter.textobj                              *gliter.textobj-gliter.textobj*

targets.vim’s quotes and separators, ported (Neovim 0.9+): text objects that
work **on** and **around** their delimiters, and that **look** for the pair
when the cursor is not inside it.


STOLEN FROM VIM                *gliter.textobj-gliter.textobj-stolen-from-vim*

From targets.vim <https://github.com/wellle/targets.vim> (2014) — the quote
text objects every Vim user installs at some point. Vim’s built-in `vi"` only
ever pairs quotes _around_ the cursor: with the cursor past the last quote on
the line it finds nothing at all. targets.vim’s fix is the whole reason this
module exists:

>
    [cursor]"word"      vi"   -> selects word   (cursor ON the quote)
    "word"[cursor]      vi"   -> selects word   (nothing ahead: looked BACK)
<

Where the cursor sits **between** two strings, Vim’s own object selects the
text **between** them (the two adjacent quotes are the pair) — a
pseudo-string nobody asked for. The plain object takes the **next string**
instead, exactly what `in"` picks there:

>
    "one" [cursor] "two"   vi"   -> selects two   (the gap goes to in"'s rule:
                                                 the NEXT pair, like targets.vim)
<

The seeking order, wherever the cursor is not on or inside a pair:

1. the **next** pair after the cursor, still on the line (a count skips
pairs, exactly like `in"` — the gap case above, and a cursor before
every string lands on the first one this way);
2. otherwise the **last** pair before the cursor, still on the line
(targets.vim calls this the `ll` range — this is where a cursor
standing after a quote goes: _back to the pair it just passed_);
3. otherwise the **nearest** pair on another line, up to `seek_lines`
lines each way — nearer line wins, and at a tie the pair _before_
the cursor ("back to the quotes you passed").

The `n` / `l` variants force a direction, and a count skips pairs (`2yin"`
yanks the second string ahead — the count keeps accumulating when it runs
past the line’s last pair, so `3in"` with two pairs left on the line and one
below finds the one below):

  -----------------------------------------------------------------------
  Key                         Object
  --------------------------- -------------------------------------------
  i" a" I"                    inside / around / inside-trimmed quotes ('
                              and ` too)

  in" an" In"                 the same, but the NEXT pair after the
                              cursor

  il" al" Il"                 the same, but the LAST pair before it

  i, a, I,                    raw-between / around / trimmed-between the
                              separators around the cursor
  -----------------------------------------------------------------------
`a"` takes the quotes and, like the built-in, the whitespace after the closing
quote — or before the opening one when there is none after. Backslash-escaped
quotes follow `'quoteescape'` (default `\`): they are content, not delimiters.


EXACTLY LIKE VIM AT THE EDGES *gliter.textobj-gliter.textobj-exactly-like-vim-at-the-edges*

- `ci"` on `""` inserts **between** the quotes — the empty region is
    completed as empty (one sacrificial space is inserted and selected,
    so the operator eats the space, never a quote; the trick is
    targets.vim’s and mini.ai’s — the space is inserted through the API
    and no `<Esc>` is sent, so the pending operator survives). `di"`
    deletes nothing; `yi"` yanks
    nothing; other operators cancel with a notice.
- `vi"` on `""` leaves exactly the selection Vim’s own `vi"` leaves —
    cursor on the opening quote, anchor on the closing one (yes, Vim’s
    own `vi"` followed by `d` eats both quotes there; so does this).
- No pair anywhere in range: the pending operator is **cancelled**, the
    way Vim’s own E348 does — nothing is changed, nothing is inserted at
    the cursor, and a notice says why. (One Vim habit to know: keys typed
    _after_ a failed object run in normal mode — gliter is no different
    from the built-in there.)
- `ci"new<Esc>` then `.` repeats — the dot-repeat recomputes the region
    at the new cursor, so it follows the buffer, not a stale position.
- `Vi"` from linewise (or blockwise) visual ends up charwise, like
    Vim’s own objects; the selection always finishes on the closing
    delimiter.


WHERE GLITER DIFFERS — AND WHERE IT MATCHES *gliter.textobj-gliter.textobj-where-gliter-differs-—-and-where-it-matches*

The whole plain-object behavior was verified against the real plugin, scenario
by scenario (a fresh process per case, `targets#o` called directly). The plain
object agrees with targets.vim on the gap between two strings too; the
remaining deliberate spots, all in the plain object:

  -----------------------------------------------------------------------
  Situation                gliter            targets.vim
  ------------------------ ----------------- ----------------------------
  cursor in the gap        the next pair     the next pair
  between two pairs on one (like in", the
  line                     requested
                           behavior)

  cursor’s line has no     the nearest       the region between the
  pair at all (plain line  complete pair by  nearest quote above and the
  between quoted lines)    line distance,    nearest quote below
                           ties to the one   (crossing lines —
                           before            distance-blind)

  cursor inside an         the nearest       the open quote paired with
  unterminated string      complete pair     the next line’s quote
  -----------------------------------------------------------------------
Everything else — inside, on, before, after the quotes; the forced
`in"`/`il"` directions and their counts, this line first then across lines;
escaped quotes — behaves like targets.vim, and the forced objects match it
exactly. `a"` takes Vim’s whitespace rule on every variant (`an"` and `al"`
included).


SEPARATORS                          *gliter.textobj-gliter.textobj-separators*

The default set is targets.vim’s:

>
    ,  .  ;  :  +  -  =  ~  _  *  #  /  \  |  &  $
<

`i,` selects the region between the nearest `,` before the cursor and the
nearest one after it — the **raw** content, spaces and all (`ci,` on `foo(a,
b, c)` changes `b`, spaces included). `I,` is the trimming twin — it strips
the spaces, tabs and newlines around the content, so `cI,` changes just `b`;
`a,` takes the commas along. The search crosses line boundaries when the list
runs over them (`multiline_sep` lines each way) — an argument list spread
over lines still selects its argument. Empty separator regions (`ci,` on
`foo(a,,b)`) behave like empty strings: the insert lands between the
separators.


EXAMPLES                              *gliter.textobj-gliter.textobj-examples*

>c
    foo("hello world", x);
<

- cursor on the `"` before `hello` — `vi"` selects `hello world`
- cursor after the closing `"` — `vi"` still selects `hello world`
    (nothing ahead, so it looked back)
- cursor on `,` — `vi"` selects `hello world` (the next pair ahead —
    what `in"` picks there; Vim’s own object would select the text
    between the two strings instead)
- cursor on `hello` — `ci"` changes the string’s inside
- `vin"` from anywhere left of the string — the same, explicitly forward
- cursor on `x` — `vi,` selects `x`; `va,` takes `, x,` along

>c
    x = compute();
    y = "a string, later";
<

- cursor anywhere on the `x = ...` line — `vi"` finds the string on the
    **next** line (lookahead crosses lines)

>lua
    local keep = "me"
    plain line, no quotes here
    local drop = "far away"
<

- cursor on the middle line — `vi"` takes the **nearer** of the two
    strings (`"me"`, one line up, beats `"far away"` two lines down); at
    an equal distance the pair _before_ the cursor wins


NOT PORTED                          *gliter.textobj-gliter.textobj-not-ported*

The `A` variants (their region is two pieces — quotes plus content minus
whitespace — which no single selection can be), pair objects (`()[]{}`, `<>`:
Vim’s built-ins already work on and inside their delimiters), argument
objects (`iaa`), and tags. **Triple-quoted strings are not detected** — `````
fences and `'''`/`"""` docstrings are just runs of single quotes, the way
Vim’s own objects read them; for those, use nvim-various-textobjs
<https://github.com/chrisgrieser/nvim-various-textobjs>. Separator objects do
not seek (the nearest one on each side is the whole idea); quote objects do.


HOW THE MAPPINGS ARE MADE *gliter.textobj-gliter.textobj-how-the-mappings-are-made*

Every idiom was verified against real Neovim 0.10 and 0.12 before shipping. The
operator-pending side is an `<expr>` mapping that computes the region and
returns one of two strings: `'<Esc>'` — which cancels the pending operator
when there is nothing to select, exactly like Vim’s E348 — or
`'<Plug>(gliter-textobj-N)'`, a plain per-object mapping that performs the
selection (cursor to the start, `normal! v`, cursor to the end; folds open with
`zv`). A dot-repeat replays the `<Plug>` keys directly, which is why the plug
**recomputes** the region instead of trusting a stashed position. The Visual
side is a plain Lua mapping: force charwise, cursor to the start, `o` (swap
corners), cursor to the end — the selection is exactly the region whichever
corner the user started from, and for an empty region it is exactly Vim’s own
inside-the-quotes selection.


OPTIONS                                *gliter.textobj-gliter.textobj-options*

>lua
    require('gliter.textobj').setup {
      quotes = { '"', "'", '`' },      -- which quotes get objects
      separators = {                   -- targets.vim's default set
        ',', '.', ';', ':', '+', '-', '=', '~',
        '_', '*', '#', '/', '\\', '|', '&', '$',
      },
      seek = true,        -- work from on/around a pair, and look next/last
                          -- (off: only the pair around the cursor, no
                          -- in"/an"/il"/al" mappings)
      seek_lines = 200,   -- how far a quote seek looks, each way
      multiline_sep = 50, -- how far a separator object searches each way
      reclaim = true,     -- re-assert the keys when something maps over
                          -- them (mappings created later win in Vim, so
                          -- the keys are re-mapped on VimEnter and audited
                          -- as you edit; false = keep whoever mapped later)
    }
<

or through gliter: `require('gliter').setup { textobj = true }`.

The mappings are operator-pending and Visual at once (`o` + `x`), so `vi"`,
`ci'`, `da\``,`yi#` all work. An object that finds nothing says so — a miss
never moves the cursor, and never inserts at it.
