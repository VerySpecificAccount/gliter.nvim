1. gliter.make                                       *gliter.make-gliter.make*

Emacs’ `M-x compile` for Neovim’s `:make` machinery: per-filetype
`'makeprg'`, a bottom output window (buffer `gliter://make`) the output streams
into with terminal colors, and its errors wired to the quickfix list (Neovim
0.9+).

Vim has had `:make` since 1992 — run `'makeprg'`, read the output with
`'errorformat'`, fill the quickfix. But it is a wait-then-look affair: the
output lands in the quickfix’s `file|line col text` dress, colors are
stripped, and nothing tells you what the command even was. Emacs’ compile
(compile.el, mid-1980s) got there decades earlier with the `*compilation*`
buffer: the command echoed at the top, the raw output scrolling by in full
dress, `next-error` cycling through the locations, and a plain normal buffer
you can search and copy from. gliter.make is that buffer, drawn on top of the
built-ins.


WHAT IT DOES                            *gliter.make-gliter.make-what-it-does*

- **Sets 'makeprg' per filetype**, from a table in opts — `'make'` for
    everything by default, `go build ./...` for go, `cargo build` for rust,
    `zig build` for zig, `cmake --build build` for cmake, `pypy3 %` for python
    (runs the file, so you get the real traceback; `python -m py_compile %`
    sits commented in the table for a syntax-check-only variant), `latexmk`
    for tex. They are ordinary buffer-local options afterwards: `:setl makeprg=...` on a buffer still wins (that buffer keeps yours), and so does
    a global `:set makeprg=...` that is not the default. `errorformats` does
    the same for `'errorformat'` (cargo’s `--> file:line:col` lines and
    python’s `File "x.py", line N, in <module>` tracebacks — both shapes —
    are spoken by default; the value is a _list_ per filetype, and each entry
    is tried on a line of its own before Vim’s default `'errorformat'` gets
    its turn — the way Emacs’ `compilation-error-regexp-alist` works, and
    unlike one merged `'errorformat'`, which cannot backtrack: a half-matching
    pattern in front eats the line before the patterns behind ever see it,
    which is exactly how python’s bare `File "x.py", line 2` of syntax
    errors used to go unrecognized).
- **Runs it the Emacs way**: `<Leader>lm` (Spacemacs’ compile key) — or
    `:GliterMake` — opens a window at the bottom, echoes the command as the
    first line, and streams stdout and stderr into it as they arrive. The
    focus stays in your buffer, like Emacs.
- **Looks like a terminal**: ANSI escape sequences in the output (SGR
    colors, 256-color and truecolor, bold, italic, underline, reverse) are
    rendered as real highlights — gcc’s red errors, cargo’s green checkmarks,
    make’s output all keep their colors. The colors are a set of
    `GliterMakeHl*` groups with the xterm palette; the text itself stays
    plain, so yanking from the buffer gives clean text.
- **Recognizes errors per line**, the way Emacs matches them: every line is
    tried against a _list_ of `'errorformat'`s — this filetype’s, then Vim’s
    default — until one recognizes it — including formats that carry no
    `file:line:col` at all,
    like python’s `File "x.py", line 2, in <module>` and the bare
    `File "x.py", line 2` of syntax errors (files not open in any
    buffer are resolved against the directory the build ran in). Every
    recognized error fills the quickfix list — the ones with a location as
    jumpable entries, the location-less ones (`error: boom`, a bare
    `SyntaxError: ...` trailer) as message-only entries — so `:cnext`,
    `:cprev`, `:cc`, `:copen` and friends always have something to step
    through; a failed run that recognizes nothing keeps the previous list
    instead of wiping it (a clean success clears it, the way `:make` does).
    The lines themselves keep exactly the colors the tool painted on them —
    no extra underline on top. The exception trailer (`SyntaxError: invalid syntax`, `NameError: ...`) becomes the entry’s message, so the quickfix
    reads the error, not the `File "..."` line that only carried the
    location.
- **Jumps land on the exact character, whatever the format said**: the
    parsed column when there is one; else, for python 3.11+, the caret line
    under the echoed source (`^^^^`, tildes in 3.13’s `~~^^~~`)
    gives column and span — translated out of the echo’s indentation (CPython
    prepends four spaces to the echoed line) into the file’s own coordinates;
    else the quoted symbols of the exception trailer (`NameError: name 'x' is not defined`) are searched on the error’s line — the first one found there
    wins, the way Emacs’ compilation lands on the offending token. The span is
    left VISUALLY SELECTED (v-mode) by `<CR>` — where Emacs’ compilation only
    flashes a face, the next key acts on exactly what the compiler pointed
    at: `c` to change it, `y` to yank it, `i` to type over it — while `n` /
    `p` only FLASH it, for a quick second (`flash` option, 1000 ms by
    default): cycling should read like a flip-book, not park selections in
    windows you are not in. The quickfix’s own stepping — `:cc`, `:cnext`,
    `:cprev`, `<CR>` in the quickfix window — flashes the same way.
- **Compilation finished at 21:15:07.** — or
    `Compilation exited abnormally with code 2 at 21:15:07.` — is the last
    line, colored green or red, exactly the sentences Emacs appends. On
    failure the output cursor is parked on the first error.
- **One build at a time**: running `<Leader>lm` again while one runs kills
    it and starts over; `:GliterMakeStop` (or `<C-c>` in the output) stops
    it with `Compilation interrupted.`
- **Runs the file in front of you, too** — the whole of a runner.lua-style
    config, one `output` function deep: `<Leader>lr` runs the current file
    (`runner.programs[filetype]`), the same key in Visual mode runs the live
    selection through an interpreter (`runner.visual[filetype]`),
    `<Leader>lp` ripgreps a pattern into the quickfix, and the
    `runner.shells` keys launch fzf / tree under `<Leader>l`. By default all of it
    goes through the same compilation buffer + quickfix (a real terminal
    where stdin is needed); one `runner.output` function of yours — a
    floating Snacks terminal, say, the example is below — reroutes all of
    it. |gliter.make-gliter.make-the-runner|


KEYS                                            *gliter.make-gliter.make-keys*

  -----------------------------------------------------------------------
  Key               Where                    Action
  ----------------- ------------------------ ----------------------------
  <Leader>lm        anywhere                 run the build ('makeprg' +
                                             any :GliterMake args again)

  n                 output                   next error location — jumps
                                             in the window the build
                                             started from, the span
                                             flashed there for a quick
                                             second

  p                 output                   previous error location,
                                             flashed the same way

  <CR>              output                   jump to the error under the
                                             cursor, the first below it,
                                             or (below the last error)
                                             the last one above — always
                                             somewhere; the cursor moves
                                             into the source window with
                                             the span selected

  r                 output                   re-run the same command
                                             (Emacs’ recompile)

  i, a, I, A        output                   type a line to the running
                                             program’s stdin — a python
                                             input(), a cat, a REPL that
                                             landed in the buffer, all
                                             answer it (the line is
                                             echoed dim, comint-style)

  t                 output                   re-run the same command in a
                                             real terminal window — for
                                             the programs that want a
                                             whole keyboard, not just a
                                             line

  q, <Esc>          output                   close the window (the buffer
                                             stays, like *compilation*)

  <C-c>             output                   stop the running build

  <Leader>lr        anywhere                 run the current file
                                             (runner.programs); the same
                                             key in Visual mode runs the
                                             live selection
                                             (runner.visual)

  <Leader>lp        anywhere                 ripgrep a pattern (prompted,
                                             prefilled with the cword) —
                                             matches in the quickfix,
                                             flashed on stepping; in
                                             Visual mode, a one-line
                                             selection is the pattern

  <Leader>lf,       anywhere                 the runner.shells launchers:
  <Leader>lt                                 fzf, tree by default
                                             (interactive ones get a real
                                             terminal)
  -----------------------------------------------------------------------
Every jump goes through `:edit`, so it lands on the jumplist — `<C-o>` walks
back through the error tour. The flash is `GliterMakeFlash` (a background face,
`combine`d over the syntax) for `flash` milliseconds; step again and the
previous flash dissolves instantly. The quickfix’s own stepping is hooked
where it happens — `:cnext` and friends do not fire `QuickFixCmdPost` (that
event belongs to the commands that _fill_ the list), so gliter watches the
command line as you type them and the quickfix window’s own `<CR>`, and
flashes the entry landed on; the list id keeps it to gliter’s own lists
(`:grep`'s, gliter.ctags' stay untouched). All keys are rows in the `keys`
table of `setup()` (`run`, `show`, `stop`, `run_file`, `grep`); set one to
`false` to disable it. The output-buffer keys are fixed, like Emacs’.


COMMANDS                                    *gliter.make-gliter.make-commands*

>
    :GliterMake [args]    run 'makeprg' (args appended: :GliterMake clean)
    :GliterMakeShow       bring the output window back and focus it
    :GliterMakeStop       stop the running build
    :GliterRun [args]     run the current file (runner.programs; args appended)
    :GliterGrep [pat]     ripgrep a pattern (prompted when absent)

OPTIONS                                      *gliter.make-gliter.make-options*

>
    require('gliter.make').setup {
      keys = {
        run = '<Leader>lm',  -- false disables the mapping
        show = false,        -- e.g. '<Leader>ls'
        stop = false,        -- e.g. '<Leader>lk'
        run_file = '<Leader>lr', -- run the file; its Visual twin the selection
        grep = '<Leader>lp',     -- ripgrep a pattern
      },
      programs = {           -- 'makeprg' per filetype; '*' = the rest;
        ['*'] = 'make',      -- a row set to false leaves that filetype's
        go = 'go build ./...',  -- 'makeprg' (or '*''s) alone
        rust = 'cargo build',
        zig = 'zig build',
        cmake = 'cmake --build build',
        -- python = 'python -m py_compile %',  -- syntax check only
        python = 'pypy3 %', -- run the file: real tracebacks
        tex = 'latexmk -pdf -interaction=nonstopmode %',
      },
      errorformats = {       -- 'errorformat' per filetype (nil = default);
                             -- a LIST: each entry gets a whole try per line,
                             -- before Vim's default — a merged format cannot
                             -- backtrack (a half-matching pattern in front
                             -- eats the line). A string still works too.
        rust = { '%E%.%#-->\\ %f:%l:%c,%Wwarning:%m' },
        python = { '  File "%f"\\, line %l%.%#' },
      },
      height = 12,           -- output window height
      ansi = true,           -- render ANSI colors (terminal look)
      scroll = true,         -- follow the output; stops when you scroll away
      env = { CLICOLOR_FORCE = '1', FORCE_COLOR = '1',
              CARGO_TERM_COLOR = 'always' },  -- false = pass nothing
      pty = true,            -- run under a pty, like Emacs' compile (below)
      width = 0,             -- the pty's width: 0 = the origin window's,
                             -- floored at 100; a number forces it
      flash = 1000,          -- ms an error's span stays flashed when n / p
                             -- (or :cnext, :cprev, quickfix <CR>) step onto
                             -- it; false = no flash
      runner = {             -- run the file in front of you (see below)
        programs = {         -- per filetype; '' = no filetype at all,
          python = 'pypy3 %',   -- '*' = catch-all (off by default),
          c = 'gcc -g % && ./a.out',  -- false = disabled, announced
          cpp = 'g++ -std=c++17 -g -Wall % 2>/dev/null && ./a.out',
          lua = 'lua %',
          rust = 'RUST_BACKTRACE=1 cargo run || rustc % -o a.out && ./a.out',
          haskell = 'runhaskell %',
          [''] = 'make',
        },
        visual = {           -- interpreters for the Visual selection
          lua = 'lua',
          python = 'python',
          javascript = 'node',
        },
        shells = {           -- launchers on <Leader>l<key>
          f = { cmd = 'fzf', interactive = true },
          t = 'tree',
        },
        grep_prog = 'rg',    -- the <Leader>lp binary: 'rg' ->
                             -- 'rg --vimgrep --color=always'; another
                             -- name -> '<bin> -rn'; false (or a binary
                             -- that is not installed) -> :vimgrep
        output = nil,        -- function(spec) — yours; nil = compilation
                             -- buffer + quickfix (terminal where stdin is
                             -- needed)
      },
    }
<

or through gliter: `require('gliter').setup { make = true }`.

`env` is merged with your environment (not a replacement) and asks the common
tools for colors over a pipe, where they default to plain text — gcc wants
`-fdiagnostics-color=always` on the command line, in the Makefile or in
`programs`.

`pty = true` **(the default)** runs the build under a pseudo terminal, the way
Emacs’ `M-x compile` does (Emacs’ `process-connection-type` is a pty since
the beginning): every tool colors itself — gcc, clang, cargo, python all
check _“is this a terminal?”_ before painting, stay plain over a pipe and
paint under a pty — and stdout/stderr interleave exactly, at the price of
long lines wrapping at the pty’s width and progress spinners turning into
lines. Emacs’ `*compilation*` buffer pays both prices too; that is what
compiler output looks like on the other side. The pty’s width is `width` —
0 (the default) tracks the window the build started from, floored at 100, so
diagnostics get room — and when nvim itself has no `TERM` (a GUI launch), the
job gets `xterm-256color` so the colors still come. `pty = false` is the plain
pipe: no wrapping, and colors only from the tools `env` can talk into.


THE RUNNER                                *gliter.make-gliter.make-the-runner*

The compile half builds the project; the runner half runs the file in front of
you — a whole runner.lua-style config, one `output` function deep:

- `<Leader>lr` runs the current file with `runner.programs[filetype]`
    (`pypy3 %` for python, `gcc -g % && ./a.out` for c, `lua %`,
    `runhaskell %`, `make` for a buffer with no filetype). A row can also
    be a table — `{ cmd = 'python -i %', interactive = true }` — to give
    that filetype’s runs a real terminal up front (stdin-ready programs).
    `%` is the
    buffer’s file — full path, shell-escaped, so names with spaces survive
    — and `%:p`, `%:h` & co. work like in `'makeprg'`; a `%s` anywhere in
    the template switches it to printf style
    (`string.format(prog, shellescape(file))`). An unknown filetype is
    announced, not guessed — give it a row, or a `['*']` catch-all. A
    modified buffer says so: the run reads the saved file, like `:make`.
- The same key in Visual mode runs the live selection through
    `runner.visual[filetype]` (lua, python, node by default): the selection
    is read from `v` to `.` — not from `'< '>`, which are only written when
    Visual mode ends and the mapping fires before that — written to a temp
    file (removed when the run is over) and piped to the interpreter.
- `<Leader>lp` greps a pattern — the prompt prefilled with the word
    under the cursor, or the one-line Visual selection under the same key
    — from the working directory. The binary is `runner.grep_prog`: `rg`
    (the default) runs `rg --vimgrep --color=always`, any other name runs
    `<bin> -rn`, and `false` — or a binary that is not installed — falls
    back to `:vimgrep`, no external tool needed. Either way every match
    lands in the quickfix (typed `I`, blue, not red — they are
    matches, not errors), flashed on stepping, and `rg`’s exit 1 reads as
    `No matches.`, not as a failed compilation.
- The `runner.shells` launchers: `<Leader>lf` fzf, `<Leader>lt` tree
    by default. Each key of the table lands on `<Leader>l<key>`; a key
    that is not a single character is used whole. Set a row to
    `{ cmd = '...', interactive = true }` for a command that
    needs a keyboard.

Where all of it goes is ONE function, `runner.output`. The default runs plain
commands through the compilation buffer — streaming, colored, errors and
matches parsed into the quickfix — and interactive ones through a real
terminal split at the bottom (`q` closes it once the process is over, `i` goes
back in), because a pipe has no stdin. Set `output` to a function of yours and
the default is out of the loop entirely — this is the `run_in_float` of a
classic runner.lua, adapted to the spec:

>lua
    require('gliter.make').setup {
      runner = {
        output = function(spec)
          Snacks.terminal.open(spec.cmd, {
            auto_close = false, -- do not close the window when the process ends
            win = {
              position = 'float',
              width = 0.9,
              height = 0.8,
              style = 'terminal',
              enter = true,
            },
          })
        end,
      },
    }
<

`spec` carries `cmd` (the whole command line, ready to run — exactly what the
default would execute), `kind` (`'file'`, `'visual'`, `'grep'` or `'shell'`),
`ft`, `file`, `interactive` (the command wants a keyboard) and `title`. A
terminal float can ignore everything but `cmd`; an output that wants to behave
differently per kind has what it needs.


STOLEN FROM EMACS                  *gliter.make-gliter.make-stolen-from-emacs*

compile.el has shipped `M-x compile` since the mid-1980s: run a command, show
its output in a `*compilation*` buffer, underline the errors, `next-error`
through them. Spacemacs puts compile a `SPC l c` away (the `l` layer holds the
language tools, `m` for make here — `SPC l m`); gliter puts it at
`<Leader>lm`. Everything here is compile.el’s choreography — command echo,
streaming, the exit sentence, the keys — with the quickfix list seated next
to `n`/`p` so both worlds work on the same errors.


LIMITS                                        *gliter.make-gliter.make-limits*

- One build at a time, one output buffer (`gliter://make`) — Emacs can
    keep several `*compilation*` buffers; gliter cannot, yet.
- The build runs in the current working directory, like `:make` — not in
    the directory of the buffer, like Emacs’ `default-directory`. The
    runner’s grep follows it: `rg` walks the working directory too.
- The default output is a pipe, but not a dead end: `i` in the output
    buffer types a line into the running program’s stdin (a python
    `input()`, a `cat`, a REPL, all answer it), `t` re-runs the command in
    a real terminal when it needs more than lines, and a
    `runner.programs` row set to `{ cmd = '...', interactive = true }`
    starts that filetype’s runs in a terminal up front. Or route the whole
    runner to your own `output` function.
- Error lines are matched one line at a time (as Emacs does), so
    multi-line `'errorformat'` entries (`%A`…`%Z` continuations that carry
    the location on a later line) are only half-recognized.
